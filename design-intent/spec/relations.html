機械層 (machine-readable) 文書前文 (この規約集の位置づけ) 2 件

本文書は folio framework の 関係性管理 spec (relation management spec)。 各 spec file 同士の関係 (置き換え / 参照 / 依存 / 拡張 等) を machine-readable に表現する規約を定める。

背景: HTML 仕様書群が増えると AI agent が全文を読まずに「どの spec がどう繋がっているか」 を把握する仕組みが必要。 本仕様は spec-graph-management-research.html (5 並列 researcher × 117 ソースの調査) の結論から、 Phase 1 採用と判断された 3 要素 (W3C 標準語彙 + JSON-LD + inventory schema) を規範化する。

本文書は IETF RFC 2119 および RFC 8174 / BCP 14 に定義される MUST / SHOULD / MAY のキーワード解釈規約に従う。

01 §0 / 読み方

§0. Reader's Guide

まず読み方から。 この規約は folio を導入した各プロジェクトと folio 自身の双方に適用され、 各 spec が head の JSON-LD で宣言した関係を build 時に inventory へ集めます。 標準語彙 (§1) → 独自語彙 (§2) → markup (§3) → inventory (§4) → 双方向 (§5) の順に読みます。

本 spec は Layer 1 consumer と folio Layer 0 自身の双方に適用し、 各 spec が head JSON-LD で宣言した関係性を build 時に inventory へ集約する前提を共有する。 読む順序は §1 標準語彙 → §2 独自語彙 → §3 markup → §4 inventory → §5 双方向。

機械層 (machine-readable) §0. Reader's Guide の地の文・運用説明・rationale 2 件

本 spec は Layer 1 consumer project および folio Layer 0 自身 の双方に適用する。 各 spec file が <head> JSON-LD で関係性を宣言し、 build 時に inventory が auto-generate される設計を前提とする。

読む順序: §1 (W3C 標準語彙) → §2 (folio 独自語彙) → §3 (JSON-LD markup) → §4 (inventory) → §5 (Bidirectional)。 規範要件 (MUST) は §1〜§4、 §5 は SHOULD レベルの informative ガイダンス。

AI agent (spec edit を行う Claude Code 等) は、 spec 編集前に本 spec § 1〜§ 3 を必読する。 編集対象 spec の <head> JSON-LD を更新する際は §1〜§2 の語彙のみを使い、 独自命名を導入しない (MUST)。 不足する関係性は §5 経由で folio amendment ADR として提案する。

02 §1 / W3C 標準語彙

§1. W3C Standard Vocabulary

関係の表し方は、 まず W3C の既存標準語彙 (dcterms / schema.org / PROV-O) を最優先で使います。 標準で表せない関係だけを、 次の §2 で folio 独自の語彙として定義します。

関係性は W3C 既存標準語彙 (dcterms / schema.org / PROV-O) を最優先で採用し、 表現できない関係のみ §2 で folio 独自語彙を定義する。

§1.1 Dublin Core Terms (DCMI)

文書間関係 (置換 / 参照 / 部分 / 要求 / 来歴) は dcterms 語彙を採用 MUST、 JSON-LD context に dc prefix を宣言する。

PROV-O (W3C Provenance Ontology) は出所・派生・寄与関係を表現する。 folio では derived-from 系の関係に採用する。

03 §2 / folio 独自語彙

§2. folio Custom Vocabulary

標準語彙で表せない folio 固有の関係 (依存・拡張・原則の実装) だけを、 folio: という接頭辞を付けて独自に定義します。 独自語彙を増やすときは ADR を起こし、 利用者の承認を得ます。

標準語彙で表せない folio 固有の関係のみ folio: prefix で独自定義し、 追加は user 承認の ADR を経る MUST。

§2.1 folio 独自語彙 (規範定義)

folio:depends-on / extends / implements の 3 語を独自定義する (URI 実体は v1.0.0 で解決可能化予定の placeholder)。

folio:* prefix で定義する独自語彙
語彙意味逆語彙W3C 代替検討

§2.2 命名規則 (standard 優先原則)

新規関係は標準語彙 → 既存独自語彙 → 新規 folio: 語彙の順で採用判断し、 独自語彙の ADR には却下理由・逆語彙・使用例を含める MUST。

機械層 (machine-readable) §2. folio Custom Vocabulary の地の文・運用説明・rationale 6 件

§1 標準語彙で表現できない folio 固有の関係性のみ、 folio: prefix で独自定義する。 独自語彙の追加は ADR を起票し constitution P-10 に準じた user 承認を経る MUST。

@context prefix: "folio": "https://folio.dev/spec/v1/" を JSON-LD context で MUST 宣言する (使用時のみ)。 URI 実体は v1.0.0 リリース時に解決可能化予定 (現在 placeholder)。

新規関係を spec で導入する際は、 以下の順で採用語彙を決定する MUST。

  • §1 標準語彙 (dcterms / schema.org / PROV-O) で表現可能か検討する
  • 表現可能なら標準語彙を使用する MUST (独自命名禁止)
  • 表現不可能 (意味が弱い / 強い / 不適合) と判断した場合、 §2.1 既存独自語彙で代替可能か検討する
  • 既存独自語彙で表現不可能な場合のみ、 新規 folio:* 語彙を ADR で提案する

独自語彙導入時の ADR には以下を MUST 含める:

  • 標準語彙で表現できない理由 (どの語彙を検討したか、 なぜ却下したか)
  • 逆語彙の有無 (双方向 dual を採用するか、 単方向で済むか)
  • 使用 spec 例 (どの spec で本語彙を使う予定か)
04 §3 / JSON-LD

§3. JSON-LD Schema in <head>

各 spec は head の中に JSON-LD ブロックを 1 個必ず持ちます。 そこに関係をどう書くか — 最小例・関係込みの例・@id の書き方・試作段階での遵守レベル — をこの章が定めます。

各 spec は head に JSON-LD ブロックを 1 個 MUST 持ち、 その関係性表現 schema を本章が規定する。

§3.1 Minimal Example (関係性なし)

関係性を持たない最小 spec の JSON-LD 例。 @type は schema:TechArticle を採用し、 独自型は使わない。

<script type="application/ld+json">
{
  "@context": {
    "schema": "https://schema.org/",
    "folio": "https://folio.dev/spec/v1/"
  },
  "@id": "./constitution.html",
  "@type": "schema:TechArticle",
  "folio:version": "0.4.2-draft",
  "folio:stakeholders": ["Developer", "AI Agent"]
}
</script>

§3.2 Full Example (関係性込み)

複数の関係性 (references / depends-on 等) を宣言する spec の JSON-LD 例。

<script type="application/ld+json">
{
  "@context": {
    "dc": "http://purl.org/dc/terms/",
    "schema": "https://schema.org/",
    "folio": "https://folio.dev/spec/v1/"
  },
  "@id": "./relations.html",
  "@type": "schema:TechArticle",
  "dc:title": "folio relations spec",
  "folio:version": "0.1.0-draft",
  "folio:stakeholders": ["Developer", "AI Agent", "External Reviewer"],
  "dc:references": [
    { "@id": "./rules.html#s4-format" },
    { "@id": "./constitution.html#s2-principles" },
    { "@id": "../research/spec-graph-management-research.html" }
  ],
  "folio:depends-on": [
    { "@id": "./rules.html" }
  ]
}
</script>

@id と参照値の記述規則 (自己 / 同一 dir / 上位 dir / section anchor の相対 path、 design-intent/ 配下は絶対 URL 禁止)。

試作段階の遵守レベル: JSON-LD ブロックと標準語彙優先は MUST、 @id 自己参照と関係性宣言は次 Phase で MUST へ昇格する。

機械層 (machine-readable) §4. Inventory Schema の地の文・運用説明・rationale 10 件

folio は全 spec の集約 index (inventory.json) を auto-generate する設計を採用する (将来の試作 plugin で実装予定)。 AI agent は inventory.json のみで全体構造を把握でき、 必要な spec だけ Read することで context window を効率的に使う。

本 §4 では schema を規定する。 inventory.json の 実体 file は作成しない (試作 plugin の folio inventory CLI で auto-generate される、 manual 作成は禁止)。

本モデルは Anthropic Agent Skills の 3-tier loading パターンに基づく (調査レポート §3.3)。 AI agent が必要分のみ読み込み、 context window を効率化する。
