3 §3 / 命名

§3. File Naming Convention

ファイルやフォルダの名前の付け方を決めます。 HTML はすべて kebab-case、 決定記録は ADR-番号-名前、 各まとまりは入口となる README を持ちます。

全 HTML file 名は kebab-case、 ADR は ADR-NNNN-<slug>、 各 cluster は README.html を持つ MUST。 vocabulary.yaml の schema は terms 配列 (canonical MUST / forbidden = gate 用)。

機械向けの詳細（原文そのまま） §3. File Naming Convention の地の文・運用説明・rationale 2 件
  • 全 HTML file 名: kebab-case.html (例: spec-taxonomy.html)。 snake_case / camelCase 禁止。
  • ADR: ADR-NNNN-<slug>.html (4 桁 ID)。
  • vocabulary (Layer 1 consumer): vocabulary.yaml (project root or design-intent/、 P-2 YAML 例外)。
  • config: folio.config.yaml (consumer project root、 P-2 YAML 例外)。
  • entry point: 各 cluster は README.html を持つ MUST (orphan 例外、 constitution P-6)。

vocabulary.yaml の schema (P-5 canonical naming SSoT): terms: の配列で、 各 entry は canonical (正準名、 MUST) と forbidden (禁止 synonym の配列 — vocabulary gate REQ-CI-013 が prose 内検出に使う) を持つ。 加えて各 entry は optional に definition (1 行定義)、 relationships (他 canonical 名との関係を述べる配列)、 flagged_ambiguities (grilling で surface した未解決の曖昧点の配列) を持ってよい。 これらは glossary を folio-architect grilling (Phase C) と spec-review-vocabulary agent の grounding として豊かにする (ADR-0031 §2.4)。 後方互換: vocabulary gate は forbidden のみ読むため、 optional field の有無は既存の gate 挙動に影響しない。

全 spec file は以下の構造を MUST 採用する。

全 spec file の <head> は (1) <meta> tag による flat metadata、 (2) <title>、 (3) <link> stylesheet、 (4) <script type="application/ld+json"> による関係性ブロックの 4 要素を MUST 含む。 JSON-LD ブロックの内容 schema は relations.html §3 に集約する。

folio spec は HTML を表現基体としており、 plain text を超える visual richness を活用できる。 domain の構造を反映する visual element を selective に採用し、 装飾でなく WHAT 表現の精度を高める手段として用いる (P-3 WHAT-only 整合)。 spec author (人間および folio-architect) は domain を grill した後、 visual cue 候補を user に推奨答えとして提示してから採用する (P-8 silently choosing 禁止)。

留意: (a) visual richness は domain 構造を反映する手段で装飾ではない — 状態を持たない domain に stateDiagram は不要、 「使わない」も正しい設計判断。 (b) diagram label / table header / state 名は vocabulary.yaml の canonical name を使う (P-5)。 (c) 図の幅は body 幅 (現状 940px) に収める — 横長 LR flow は縮小されて文字が潰れるため、 線形 flow / pipeline は原則 top-down 配置 (top-level は flowchart TB / graph TB、 subgraph 内は direction TB) で縦に伸ばし幅内に収める; node 過多 (> 20) や top-down でも収まらない wide 図 (並列 lane・tree 等) は分割または <details> で hide する; どうしても wide な図は figure.diagram 内 pre.mermaid の横スクロール fallback に委ねる (§4.6 で focusable 規定)。 mermaid の subgraph タイトルは単行にする — <br> で多行タイトルにすると mermaid が cluster-label の縦 padding を 1 行分しか確保せず 2 行目が子ノード/枠に overlap するため、 補足 (例「7 並列固定」) は単行に畳むか figcaption / accDescr に置く (node label の <br> は node が自動 sizing するため可)。 これは folio validate の render-safety gate (REQ-VER-021) が <pre class="mermaid"> 内の subgraph 多行タイトルを機械検査する (render 後の幾何 overlap を static pattern-lint で捕捉)。 (d) mermaid loader 未 load 時でも <pre class="mermaid"> の raw syntax は人間に読める形のままにする (graceful degradation)。 (e) folio-architect による grill 中の声かけ手順は refs/grilling-protocol.md ## 視覚表現レパートリー 参照。

spec HTML 内の text および diagram 内 text は WCAG 2.2 SC 1.4.3 Level AA (normal text 4.5:1 / large text 3:1) の contrast ratio を満たす MUST (w3.org/TR/WCAG22/#contrast-minimum)。

spec HTML は <head> に <meta name="viewport" content="width=device-width, initial-scale=1"> を持つ MUST — viewport meta が無いと実機 mobile browser は仮想幅 (約 980px) で render して縮小表示し、 responsive CSS が発火せず可読性が崩れる (WCAG 2.2 SC 1.4.10 Reflow の前提)。 folio init seed と folio build 生成物 (index / glossary) は付与済で、 authored spec 側の欠落は folio validate の readability-floor gate (REQ-VER-023) が機械強制する。

mermaid 図表は以下を満たす MUST:

  • accTitle および accDescr directive を付与する (WCAG 2.2 SC 1.1.1 non-text content / mermaid a11y、 mermaid.js.org/config/accessibility.html)。
  • classDef / style で fill を override する場合、 同 declaration 内で color を paired 指定する (themeVariables.primaryTextColor 継承による text contrast 不足を防ぐ)。 stroke は theme default の 3:1 contrast 維持を許容するが、 visual separation が確保されない場合は paired 指定する SHOULD (WCAG 2.2 SC 1.4.11 graphical objects)。
  • body 幅を超えて横スクロールが生じる図 (figure.diagram 内の render 済 <pre class="mermaid"> = 図そのものが overflow した場合) は tabindex="0" で keyboard-focusable にする MUST (WCAG 2.2 SC 2.1.1 Keyboard / axe scrollable-region-focusable、 dequeuniversity scrollable-region-focusable)。 scroll 容器は figcaption を含む figure でなく内側の pre.mermaid に限定する (figcaption の xref tooltip 等による spurious overflow を避ける)。 folio では initialize script が render 後に overflow した pre.mermaid へ tabIndex を付与し、 併せて role="region" + 図 title 由来の aria-label で scroll 領域を screen-reader に明示する (§8 read-only enhancement、 <pre class="mermaid"> raw fallback は不変)。

根拠と HOW knowledge は refs/html-spec-craft.md §1 (WCAG 2.2 verbatim quote 集) + §2 (mermaid a11y 仕様 + paired override 正攻法) を参照。 mermaid 公式 docs に primaryTextColor 継承の直接記述は不在のため、 本 rule は (a) mermaid 公式の nodeTextColor 継承定義 と (b) folio の paired-override 規約を分けて根拠化している (refs/ §2.3)。

7 §7 / dual-audience

§7. Dual-Audience Markup (data-audience taxonomy)

1 つの HTML を機械向け (精密) と人間向け (要約 + 図) の両方に同時に書く方法です。 採用は任意ですが、 採用したら守るべき構造のルールが決まっています。

spec を機械向け (精密 normative = SSoT) と人間向け (essence + 図) の双方へ 1 HTML に co-author する markup。 採用は任意だが採用 spec は §7.3 invariant 遵守 MUST (conditional-normative)。 consistency は二層 enforcement (floor / ceiling) で担保。

§7.1 data-audience taxonomy

data-audience は closed 2 値 (machine | human) の canonical 属性。 synonym は P-5 で禁止、 継承無く明示付与のみ。 presentation 要素にも付与でき、 REQ-DA-STRUCT-1 MUST は req container のみ。

§7.2 Canonical markup pattern (2 form)

requirement は 2 form (card / spec-row) で human essence と machine normative を data-audience + fold で co-author。 machine 部は DOM 常在・aria-hidden 無し・視覚のみ畳む。 id・badge・ears-id は一致、 EARS pattern は data-ears-pattern が SSoT。

<section class="req" id="req-xxx-001" data-audience="human">
  <div class="req__card">
    <span class="badge badge--req">REQ-XXX-001</span>
    <span class="req__ears req__ears--event">Event-Driven</span>   <!-- EARS badge (§6) -->
  </div>

§7.3 Dual-Audience Safety Invariants (conditional-normative floor)

dual-audience 採用 spec は REQ-DA-STRUCT-1〜5 の構造 invariant 遵守 MUST。 floor (validate) が両 form を data-audience=human で一律検査。 fidelity は ceiling (spec-review-fidelity) が担う。

REQ-DA-STRUCT-1必須機能オプション

dual-audience を採用する spec の各 [data-audience="human"] requirement container は [data-audience="machine"] 子孫を持つ MUST (孤立 human の排除)。

やさしく言うと人間向けに書いた要件には、必ず対になる機械向けの精密な文を同じ場所に入れます。片方だけの要件は認めません。

正確な条文（機械向けの厳密な書き方）

REQ-DA-STRUCT-1: WHERE a spec adopts the dual-audience pattern, each [data-audience="human"] requirement container (verbose card または compact spec-row) SHALL contain a [data-audience="machine"] descendant (派生元の存在保証、 孤立 human の排除)。

REQ-DA-STRUCT-2必須機能オプション

requirement-id は container id ・ .badge--req text ・ machine .ears-id text 間で case 正規化して一致する MUST。

やさしく言うと同じ要件を指す 3 か所の ID (囲みの id・人間向けバッジ・機械向け表記) は、大文字小文字を揃えたうえで一致させます。

正確な条文（機械向けの厳密な書き方）

REQ-DA-STRUCT-2: WHERE a spec adopts the dual-audience pattern, the requirement-id SHALL be consistent (case-normalized) across the requirement container id (section / details), the .badge--req text, and the machine .ears-id text。

REQ-DA-STRUCT-3必須機能オプション

全 data-audience 値は machine か human のみ (synonym 禁止、 P-5)。

やさしく言うと読者の区別に使う値は「機械向け」と「人間向け」の 2 つだけです。似た意味の別名は使いません。

正確な条文（機械向けの厳密な書き方）

REQ-DA-STRUCT-3: WHERE a spec adopts the dual-audience pattern, every data-audience value SHALL be one of machine or human only (no synonym、 P-5)。

REQ-DA-STRUCT-4必須機能オプション

machine 部 ([data-audience="machine"]) は aria-hidden を持たない MUST NOT (AI / accessibility-tree からの normative 不可視化を防ぐ)。

やさしく言うと機械向けの部分に「読み上げから隠す」印を付けてはいけません。AI や支援技術から正式な条文が見えなくなるためです。

正確な条文（機械向けの厳密な書き方）

REQ-DA-STRUCT-4: WHERE a spec adopts the dual-audience pattern, the machine part ([data-audience="machine"]) SHALL NOT carry aria-hidden (AI / accessibility-tree からの normative 不可視化を防ぐ)。

REQ-DA-STRUCT-5必須機能オプション

human EARS badge (req__ears--<p>) は machine data-ears-pattern と整合する MUST (短縮形 alias を正規化して比較)。

やさしく言うと人間向けに出す要件の型バッジは、機械向けに記録した型と食い違ってはいけません。

正確な条文（機械向けの厳密な書き方）

REQ-DA-STRUCT-5: WHERE a spec adopts the dual-audience pattern, the human EARS badge (req__ears--<p>) SHALL agree with the machine data-ears-pattern (短縮形 alias を正規化して比較)。

§7.4 Human view guidance (Hybrid)

human view (concept 図 / list / coverage RTM / EARS badge / fold) は §4.5 menu に集約、 強制しない guidance (author 判断、 P-8)。 普遍性は tiered (core/RTM 普遍、 図・list は section 依存、 coverage opt-in)。

機械向けの詳細（原文そのまま） §7. Dual-Audience Markup (data-audience taxonomy) の地の文・運用説明・rationale 9 件

本 §7 は spec を machine (精密 normative = canonical SSoT) と human (essence + graphical = 派生 view) の双方に向けて 1 HTML artifact に co-author する dual-audience pattern の markup 規約を定める (ADR-0033、 P-2 HTML)。 採用は任意 (opt-in) だが、 採用する spec は本 §7 の safety invariant (REQ-DA-STRUCT-1〜5) を遵守する MUST = conditional-normative。 consistency は機械的導出でなく enforcement で担保する (1-DOM co-author は prior art 無しの novelty、 ADR-0033 §2.4): floor = folio validate の dual-audience 構造検査 (本 §7.3 の REQ-DA-STRUCT)、 ceiling = Phase F の spec-review-fidelity agent (意味的 fidelity)。

  • data-audience = closed 2 値 core (machine | human)、 canonical。 AI 抽出 ([data-audience="machine"]) の決定性と floor 検査の単純化のため 2 値固定。
  • synonym (data-reader / data-for 等) は P-5 (1 entity = 1 canonical name) により禁止。
  • 継承 (cascade) は無い = 明示付与のみ (fold 境界と 1:1 対応させ曖昧さを排除)。
  • data-audience は requirement container (§7.2 の 2 form) 以外の presentation 要素にも明示付与できる — 例: 章要旨 p.section-essence (§11.5) への human、 informative 地の文の降格 wrapper への machine (ADR-0040)。 REQ-DA-STRUCT-1 の「machine 対応部 MUST」は requirement container (<section>/<details> 起点の floor 走査) にのみ適用され、 単独の presentation 要素には適用されない。

dual-audience の 1 requirement は 2 つの正規 form のいずれかを採る。 いずれも human (派生 view、 既定可視) と machine normative (canonical SSoT) を data-audience + <details> 視覚 fold で 1 unit に co-author し、 machine 部は DOM に常在 (AI / accessibility-tree / find-in-page に可視) して視覚的初期表示のみ畳む。 aria-hidden を machine 部に付けない (accessibility-tree から消すと Playwright 等 AI からも不可視となり「AI は読める」目的に反する、 ADR-0033 §2.2 verified)。 floor は container class でなく data-audience="human" semantic で両 form を一律に被覆する (ADR-0033 §2.5、 §7.3)。

form 1 — verbose card (<section class="req">。 essence を常時可視に展開、 解説密度が要る個別要件向け):

form 2 — compact spec-row (<details class="spec-row">。 1 行 1 REQ = 最小読量、 多数の要件を一望する section 向け。 summary に essence、 fold 内に machine normative。 reference 実装 = verification.html §3):

規約 (両 form 共通): (a) 要件 container の id (小文字、 section / details いずれも) ・ .badge--req text ・ machine .ears-id text は同一 requirement-id (大小文字正規化で一致)。 (b) human badge の CSS class suffix (req__ears--<p>) は EARS pattern key を用いる (2 語 pattern は common.css の短縮形 event / state = canonical event-driven / state-driven の alias)。 (c) machine normative の pattern は data-ears-pattern (full form = SSoT)。 (d) reference 実装 = verification.html §3 (form 2 compact spec-row を flagship に採用、 form 1 verbose card は本 §7.2 の例示)。

dual-audience pattern を採用する spec は次の構造 invariant を満たす MUST。 これらは folio validate の dual-audience gate (deterministic floor、 ADR-0020 scope 拡張) が機械検査する。 検査は §7.2 の verbose card (section.req) と compact spec-row (details.spec-row) の両 form を data-audience="human" semantic で一律被覆する (container class 非依存)。 意味的 fidelity (essence が normative を忠実要約か) は floor の対象外で、 ceiling = spec-review-fidelity agent が担う (二層 enforcement、 ADR-0028 / ADR-0033 §2.4)。

REQ-DA-STRUCT-5 の解釈 (ADR-0033 literal からの refinement): ADR-0033 §2.4 は REQ-DA-STRUCT-5 を「JSON-LD status と human badge の status 一致」と記すが、 現 canonical pattern (verification.html §3) は per-card JSON-LD / per-card status を持たない (status は doc-level)。 per-card で意味を持つ整合 key は EARS-pattern であるため、 floor は -5 を EARS-pattern 整合として実装する。 ADR literal の「status 一致」は per-card JSON-LD を導入する Option A' (ADR-0033 §2.3 roadmap) 採用時の future check として保留する。 同様に -2 も per-card JSON-LD @id でなく requirement container id (section / details) / badge / ears-id text の整合として実装する (実 pattern 準拠)。

human 向け graphical view の構成要素 (concept flowchart / compact REQ list / coverage RTM / EARS keyword 色 badge / <details> fold) は §4.5 の visual richness menu に dual-audience 用 row として集約する。 これらは強制しない guidance (author・folio-architect 判断、 P-8 silently choosing 禁止)。 普遍性は tiered: dual-audience core (data-audience + fold + essence) と trace RTM は普遍、 concept 図 / compact list は適用可能な section、 coverage 列 (verified/scenario) は verification mapping を持つ spec の opt-in (ADR-0033 §2.6)。

§8. JavaScript Governance (read-only enhancement only)

文書の中で JavaScript を使う範囲を定めます。 JS は見た目の補助だけで、 要件などの内容そのものは常に静的な HTML が持ちます。

spec HTML 内の JavaScript の使用範囲を定める。 原則は JS = render/view の read-only enhancement に限り、 normative content (定義/要件/MUST) の SSoT にしない (canonical は常に static)。 JS 含む spec は本章遵守。

REQ-DA-JS-1必須機能オプション

JS は static DOM 由来の read-only view enhancement に限り、 normative content (定義 / 要件 / MUST) の SSoT にしない MUST。

やさしく言うとJavaScript は静的な HTML の中身を見やすくする補助だけに使い、要件や定義そのものを JS で持たせません。

正確な条文（機械向けの厳密な書き方）

REQ-DA-JS-1: WHERE a spec includes JavaScript, the JavaScript SHALL be limited to read-only view enhancement derived from static DOM content, and SHALL NOT hold the SSoT of any normative content (定義 / 要件 / MUST)。

REQ-DA-JS-2必須機能オプション

やさしく言うとJavaScript を切っていても全文が読めるようにします。外部サーバーから読み込む書き方は使わず、部品は同梱します。

正確な条文（機械向けの厳密な書き方）

REQ-DA-JS-2: WHERE a spec includes JavaScript, the spec SHALL remain fully readable with JavaScript disabled (progressive enhancement), SHALL vendor its libraries (no runtime CDN), and SHALL NOT use ES modules with fetch() (file:// で null origin CORS により破綻、 verified)。 vendoring 違反のうち runtime-CDN script (<script src="http(s)://…"> および protocol-relative src="//…") は folio validate の dual-audience gate が 機械検出する (escaped 例・<pre> 内 raw 例は mask、 ADR-0039 §2.5)。 検出は 単一行 tag の試作 heuristic — 行跨ぎ tag は守備範囲外で、 網羅は ceiling の領分 (folio の corpus 慣習は単一行 script tag)。 conformance: scenarios/validate-violations.yaml (cdn-script.html seed、 double/single-quote 両形)。

§9.5 Glossary terms (Class B、 vocabulary.yaml SSoT + explicit/auto-mark hover tooltip)

glossary 用語 (Class B) は defined-object (Class A) の no-gaps とは別の best-effort tier で、 runtime SSoT は vocabulary.yaml の definition、 glossary view はその生成 projection とし定義を二重化しない (P-7)。 flip した self-host の edit-SSoT は glossary contract YAML。

正確な条文（機械向けの厳密な書き方）

  • JS rich tooltip は前方互換 roadmap: no-JS markup (href + data-tooltip) は将来 JS (同属性を読む rich/cross-doc preview) と前方互換で非破壊に重ねられる (§8 準拠、 1.0.0 core 非搭載)。

glossary 用語 (Class B) は defined-object (Class A) の no-gaps とは別の best-effort tier である (自然語の全 occurrence 検出は NLP 難問ゆえ term 完全性は約束しない、 ADR-0034 §2.8)。 用語の SSoT は vocabulary.yaml の definition field (§3 schema、 ISO 704 concept model: canonical = 主 designation / definition = concept 定義)。 HTML 上の glossary view は vocabulary.yaml からの生成 projection とし、 定義を二重化しない (P-7)。 この SSoT は runtime 読取り先の宣言であり、 編集の正本 (edit-SSoT) の帰属は flip 状態で分かれる (ADR-0052): SSoT-first に flip した folio 自身では edit-SSoT は glossary contract YAML 側にあり、 vocabulary.yaml はそこからの生成 projection (projection stale gate が byte 一致を保証)、 glossary.html は folio build が pack pipeline へ委譲して生成する (build-orchestrates-pack); flip しない Layer 1 consumer では vocabulary.yaml が edit-SSoT を兼ね、 glossary.html は folio build がそこから derive する (ADR-0036、 語彙は ADR-0051 §2.3)。

  • explicit-mark: domain: consumer 用語 (folio 解説不能) と任意の手動 mark は <span class="term" data-term="<canonical>">表示語</span> で明示する (REQ-GLOSS-001)。
  • auto-mark (opt-in best-effort): domain: folio-closed 用語は、 opt-in した doc (<meta name="folio-glossary-automark" content="enabled">) で folio fix が doc 初出を <span class="term"> に自動 mark する (hover tooltip のみ・glossary.html へはリンクしない、 REQ-GLOSS-002)。 いずれの方式も auto-detect で全言及を gap-lint することはしない (best-effort tier、 自然語の全 occurrence 検出は NLP 難問ゆえ doc 初出のみ・完全性は約束しない)。 consumer-domain 用語への auto-mark 越権はしない。
  • data-tooltip は生成: folio fix が marked term の data-tooltip を vocabulary.yaml の definition から materialize する (定義は vocabulary.yaml に一元化し HTML へ重複させない — runtime 読取り先は flip 状態に依らず vocabulary.yaml、 edit-SSoT の帰属は本節冒頭 carve-out に従う)。 Class A xref と同じ no-JS CSS tooltip 機構 (§9.3) を dogfood して共用する。
  • 整合は enforce: marked term の resolve (data-term → canonical) と consistency (data-tooltip → definition) は folio validate の glossary gate が block enforce する (§9.4 と同じく本節は marking 規約 = WHAT を定め、 gate 挙動の正本は verification REQ-VER-019 に一元化)。 best-effort tier ゆえ未 mark の言及は gap-lint しない。

trigger の self-host↔consumer carve-out (ADR-0052): trigger の「vocabulary.yaml を resolve」は本 §9.5 冒頭 carve-out の両経路いずれでも成立する (consumer = 直接 derive / flip した self-host = pack 委譲 + projection、 機構の正本は §9.5 冒頭 carve-out)。 いずれの経路でも vocabulary.yaml は常に存在し、 folio validate がこれを resolve して glossary gate を発火するため、 本 REQ の SHALL 本体 (上記 p.ears) は不変に発火し self-host 側に被覆穴を作らない。 本 aside は trigger の読み方のみを確定し SHALL 本体を変えない。

本 §10.3 は「いつ ADR を書くか」 の判定基準 (worthiness) を normative に集約する (ADR-0031 §2.5、 mattpocock grill-with-docs の "offer ADRs sparingly" を folio 化)。 folio-architect の grilling (Phase C) 中に decision が surface した際の offer 基準であり、 ADR の起票手順・user 承認 gate は decisions/README §5 に従う (P-7: 手順は重複させない)。

3 条件がすべて真の時のみ ADR を offer する (sparingly)。 いずれか 1 つでも偽なら ADR にしない — 可逆な決定 / context 無しで自明な決定 / trade-off の無い決定は spec 本文 (WHAT) や vocabulary.yaml に吸収し、 重厚な ADR (HTML+JSON-LD、 user 承認) を濫造しない。 folio の高コスト ADR と高い 3 条件 bar は相互補強する (少数精鋭に絞る価値が高い)。

ADR-less ≠ orphan (照会 graph との関係): 3 条件を満たす決定が無い文書一式が ADR を持たないのは正当な状態であり、 それ自体は照会 graph の欠陥ではない。 照会 graph の不変条件は「principle 終端への到達」であって ADR の有無ではない — 終端充足は ADR 内蔵 principle / 上位層 constitution への照会 / 自前 constitution のいずれでもよい。 原則接地を意図的に持たない文書一式は、 その意図を理由付きで明示宣言する — 「接地する」か「持たないと明言する」かの二択で、 照会 graph 検査が禁止するのは無言の欠落だけである (宣言 field・rationale 必須・可視一覧などの機構詳細は design-system generator README が正本)。

機械向けの詳細（原文そのまま） §11. Human-First Presentation (P-14) の地の文・運用説明・rationale 12 件

本 §11 は P-14 (Human Readability) が rules へ委任する presentation 規律を定める。 核はページ種別ごとの主たる人間読者層の定義と表示層 remediate の分業 (ADR-0039 §2.1 / §2.9) で、 これに既定表示 (§11.3)・検査手続き (§11.4)・人間層圧縮 (§11.5、 ADR-0040) が連なる。 機械読者 (AI agent) への正確さは全ページ種別で維持する (dual-audience の machine 側は §7 のまま不変)。 提示に関わる判断 (見せる / 折る / 削る) は本節の読者層定義を物差しとする。

表示層の regen は folio build が一元所有する MUST — index (landing) / glossary / 非生成ページの chrome の生成・維持 (「nav-regen-drift 系の violation は build で直す」)。 ただし pack が生成する canonical spec (生成 spec) は chrome-less — 生成 spec に対して folio build はページ内目次 (nav.toc) と breadcrumb を注入せず、 script 注入の audience-toggle も行わない (skip-link は focus 時のみ可視で存続、 prev-next は下部導線として存続し、 所属 locator を prev-next の直上に置く)。 生成 spec の提示層は pack assembler が完結所有する。 ADR-0054 §2.1 が本項の「全ページ chrome」を生成 spec について supersede する (chrome 注入は非生成ページに対して存続)。 folio fix は graph の materialize 専任 — reverse-link (REQ-REL-002) / xref wrap (§9.4) / tooltip 再生成。 folio validate の violation message は対応する remediate tool を名指しする MUST (どの違反をどちらで直すかの迷いを消す、 ADR-0039 §2.9 の実現)。 readability-floor (REQ-VER-023) のうち landing 系は build が remediate し、 viewport / essence は authoring の責務 (機械 regen の対象外)。

chrome 要素集合 (提示層正本): folio build が注入・維持する chrome 要素は下記の 9 種で尽くされ、 各要素の出力可否は「非生成ページ / 生成 spec」の別と要素ごとの出力条件の 2 つで決まる。 本節が chrome 要素集合の提示層正本 (SSoT) であり、 verification.html REQ-NAV-008 の列挙は検査が enforce する集合である。 乖離した場合は本節を優先し検査を追随させる (ADR-0054 §2.1)。 上項の「生成 spec の提示層は pack assembler が完結所有する」が指すのは本文 (body) の提示層であり、 下記のうち生成 spec でも出力される chrome 要素は、 生成 spec においても folio build が所有・維持する (本文所有と chrome 所有は別)。 なお 3 つの marker 領域 (folio:chrome-top / folio:chrome-toc / folio:chrome-bottom) は生成 spec でも常に置かれる — 抑制されるのは領域の中身であって領域自体ではない (3 領域構造は不変)。

  • skip-link (a.skip-link) — 非生成ページ・生成 spec とも出力する。 条件: skip 先 id が解決するとき (ページ内目次の最初の target → 目次 0 行なら fallback で body 内最初の id)。 どちらも解決しなければ省略する。 生成 spec でも accessibility ゆえ存続し、 focus 時のみ可視。
  • breadcrumb (nav.breadcrumb) — 非生成ページのみ出力する (生成 spec には注入しない)。 条件: 非生成ページで常時。 生成 spec の所属提示は下部の所属 locator が代替する。
  • BreadcrumbList JSON-LD — 非生成ページのみ出力する。 条件: breadcrumb への併注入であり、 かつ folio.config.yaml の base_url が設定されているときに限る (未設定なら出力しない = file:// 閲覧を壊さない二段構え)。
  • cluster-nav (nav.cluster-nav) — 非生成ページのみ出力する。 条件: そのページが README.html であり、 かつ列挙対象 (実在する兄弟 cluster の README / vocabulary が解決する corpus での glossary) が 1 つ以上あるとき。 生成 spec は README でないため該当しない。
  • ページ内目次 (nav.toc) — 非生成ページのみ出力する (生成 spec には注入しない)。 条件: 目次行 (h2/h3 から 2 段 fallback で解決した target) が 1 行以上あるとき (0 行なら目次 nav 自体を省略)。 生成 spec では章帯の節番号が同じ役目を担う。
  • 所属 locator (p.doc-locator) — 生成 spec のみ出力する (非生成ページには注入しない)。 条件: cluster 配下のページであること (chrome 注入対象は spec/ decisions/ research/ 直下ゆえ、 生成 spec では実質常時)。 位置は prev-next の直上。
  • prev-next (nav.prevnext) — 非生成ページ・生成 spec とも出力する。 条件: chain 上の隣接 (前 または 次) が実在するとき。 順序 SSoT は spec = spec/README.html の dc:hasPart 順 / decisions = 実在 ADR file の昇順隣接で、 research・README 自身・順序 SSoT に不在のページ (constitution) は chain 対象外。 chain に属していても隣接を持たない単独メンバでは出力しない (検査側も同一述語で条件付ける)。
  • print 全展開 handler (beforeprint / afterprint) — 非生成ページ・生成 spec とも出力する。 条件: 常時 (chrome の inline script に無条件で含める)。 生成 spec での audience-toggle 撤去はこの handler を巻き込まない (§11.3)。
  • audience-toggle 生成 JS — 非生成ページのみ出力する (生成 spec には注入しない)。 条件: 非生成ページで常時 script を注入する (toggle UI 自体は data-audience 要素を持つページでのみ実行時に生成される = progressive enhancement)。

ページ種別ごとの既定表示 (初見で何が見えるか) を次のとおり定める。 適用対象は living spec・生成物・新規 ADR template — frozen 文書の本文は不変 (折り畳み化は本文改変のため適用しない):

  • landing (index.html) — 全可視 (折り畳みゼロ)。 cluster 一覧の status group のみ量で畳む (>8 entry)。
  • spec 本文 — 既定 = 人間プレゼン型 (ADR-0040 が旧「バランス型」(ADR-0039 §2.4) を改訂): 見出し・章要旨 (§11.5)・図・表・REQ essence は可視 / EARS 全文 (§7.2 spec-row の machine 部) と data-audience="machine" へ降格された informative 地の文は既定で非表示 — audience-toggle で全文へ 1 操作。 no-JS 環境は全文可視へ graceful degrade (§11.5)。
  • 新規 ADR template — Context・Decision 可視 / 詳細は fold。
  • fold のネストは 2 段上限 MUST、 <summary> には要旨 1 文 MUST (空 summary・「詳細」のみの summary を禁止)。 この 2 つは現状機械 gate を持たない — authoring 規律 + Phase F review (ceiling) が担い、 違反頻度を見て floor 化を判断する (ADR-0039 §2.7 の warn→block と同じ昇格規律)。
  • 印刷時は全展開 — chrome の inline script が beforeprint で閉じた <details> を一時 open し afterprint で復元する (author CSS では closed details の中身を描画できないため script が担う、 §8 read-only enhancement)。 帰属: この handler は生成 spec でも folio build が chrome として注入・維持する (pack assembler は emit しない)。 生成 spec でも skip-link / print 全展開 handler / 所属 locator / prev-next (chain 隣接時) は同様に folio build 所有の chrome であり、 ADR-0054 §2.1 が生成 spec について落とすのはページ内目次 (nav.toc) / breadcrumb / audience-toggle 生成 JS の 3 点に限る。 pack assembler が完結所有するのは本文 (body) の提示層であって chrome 要素ではない (要素ごとの完全集合は §11.2)。

audience-toggle (ADR-0039 §2.5): chrome の inline script が、 data-audience 要素を持つ page にのみ「両方 / 人間向け / 機械向け」の 3 状態 toggle を生成する (no-JS では UI 自体が存在しない = progressive enhancement)。 適用範囲: 本項は chrome 注入を受ける非生成ページに適用する — pack が生成する canonical spec (生成 spec) は chrome-less ゆえ toggle を持たず、 人間層 / 機械層の切替は各 fold (機械層 fold・要件の正確な条文 fold) の開閉が担う (ADR-0054 §2.1 が本項を生成 spec について supersede)。 初期状態は「人間向け」 — script が toggle 生成と同時に body class audience-human を付与する (既定 = 人間プレゼン型、 ADR-0040。 script 経由ゆえ no-JS では class が付かず全文可視 = graceful degrade。 static HTML / DOM は全文を保持し続けるため AI・検索・印刷への影響はない)。 実装は body class 切替のみ (audience-human = machine 精密部を隠す / audience-machine = human 派生 view を減光)・DOM 構造不変・永続なし (状態はページ内のみ)。 連続閲覧の煩わしさが実機 walk で実証されたら localStorage 昇格 (graceful degradation 付き) する片道を注記する。 closed <details> の中身は UA の rendering skip ゆえ author CSS では開けない — 開閉は読者操作に委ねる (toggle の設計境界)。

「読める」の検査は三層で行う。 下層 = 機械 (deterministic): readability floor (REQ-VER-023) + render-gate ceiling (REQ-VER-022、 幾何 detector 6 class × 3 viewport + screenshot artifact)。 幾何が clean でも読みにくい page はある — その上層 2 手続きを presentation 変更時の必須 step と定める (適用 trigger = ページ追加 / template・chrome・common.css の変更 / spec-row 等の表示構造変更):

  • readability review lens (常設、 MUST) — 「初見の外部開発者として index から歩く」persona-based の LLM review を回す。 §11.1 の読者層定義と P-14 を検査観点に持ち、 幾何でなく読書体験 (導線が切れていないか・初見で迷子にならないか・既定表示で要旨が掴めるか) を検査する。 常設形態 = plugin root agents/readability-walk.md (spawn して使う。 本討論の監査 lens の常設化、 ADR-0039 §2.8)。
  • user 実機 walk (MUST) — template 変更を含む presentation 変更は、 user の実機 walk (公開 site または local 配信での目視) を close/release 前の必須 step とする。 「読める」の最終検査器は人間であることを手続きとして認める (P-14 の限界認識と対)。 render-gate の screenshot artifact は walk の補助材料。

この 2 手続きは LLM review + 人間の目視ゆえ非決定的で、 機械 gate (CI) を持たない (ADR-0028 §2.3 の LLM-ceiling 非搭載と同根拠)。 実施は authoring 規律 + Phase F / 独立 ceiling review が担保し、 違反 (lens/walk を踏まない presentation 変更の ship) を review が指摘する — §11.3 の fold 規律と同じ昇格規律 (違反頻度を見て floor 化を判断) に従う。

人間層 (既定表示で可視の内容) は制限時間付きプレゼン、 機械層は無制限の原稿とする (ADR-0040)。 本節が圧縮基準 (folio 自身の living spec 対象) の単一 SSoT であり、 migration 道具と folio-architect の presentation pass の双方がここを参照する — 道具側に基準を複製しない。 適用範囲の改訂: 生成 SRS プレゼン (consumer が機械 SSoT から生成する要件定義書) には本節の長さ基準でなく §12 の design system 生成 + floor 刷新 (visual-first) が適用される (ADR-0041 §2.5 / ADR-0042 が ADR-0040 を改訂)。 folio 自身の living spec (本 rules を含む) の人間層は ADR-0041 適用範囲の拡張パックが後追いするまで本節の規律下に留まる。

  • time-box — 人間層可視 prose は 1 ページ 目標約 6,000 字 (読了 10 分) SHOULD / 上限約 12,000 字 (20 分) MUST (読速 500〜600 字/分で較正。 表中テキストは線形読書しないため満重みで数えない — 計測の詳細は floor 実装 (REQ-VER-023 の可視 prose 上限 arm (warn) が定め、 migration 後の corpus 実測で再較正する)。
  • 章要旨 — 各章 (h2/h3 単位、 構造章) の冒頭に <p class="section-essence" data-audience="human"> で 1〜3 文の要旨を置く MUST (living spec の圧縮対象ページ)。 短小規約章 (単文 MUST のみの h3 等) は、 親章の essence がその核 MUST を運ぶ場合に限り省略してよい — floor の presence 検査は v1 page 単位ゆえ章単位の gap は ceiling (Phase F fidelity / readability lens) が拾う。 章要旨は当該章の降格 prose の正確な要約であり、 REQ essence (requirement 単位、 §7.2) とは粒度の異なる入れ子 — fidelity (章要旨 ↔ 地の文) は Phase F review が検査する。
  • 章図 — 構造 (依存・流れ・階層・状態) を持つ章は mermaid 図を持つ SHOULD。 図の語彙は mermaid (vendored) + §4.5 の HTML/CSS パターン (表・カード・callout・badge) に限る。 mermaid source はテキストとして機械可読 = 図自体が dual-audience。 手書き inline SVG は opt-in 例外 (採用時は独立 ceiling review 必須 MUST — 幾何 gate 較正外のため)。 ラスター/外部生成画像は MUST NOT (SSoT 外で腐る、 P-2)。

data-doc-scope による engine / pack 標識: 本章が導入する規律は data-doc-scope 属性で標識する。 値は closed 2 値 (core | srs-pack)、 canonical (synonym は P-5 禁止、 data-audience と直交する別 taxonomy — 本値 core は §7.1 の data-audience を指す「closed 2 値 core」とは別 entity の標識値)。 core = doc-type 非依存の普遍メタ規律 (エンジンコア候補)、 srs-pack = SRS 核 (γ) 固有の規律・部品 (SRS 核の外を後追いする「拡張パック」とは別概念 — 前者は核内、 後者は核外)。 grep data-doc-scope="core" は普遍コア抽出の地図であり、 core 規律の普遍化が要る doc-type が現れた際 (rule of three) の抽出単位を標識する。 既存 §1〜§11 は本属性を持たない。

エンジンコア規律 (普遍メタ、 doc-type 非依存):

  • 機械 SSoT からの生成 (derive) — 設計された高密度の人間プレゼンを corpus 規模で手 co-author するのは維持不能なため、 人間プレゼンは機械 SSoT から別ファイルとして生成する (ADR-0033 §2.3 が roadmap に残した Option A' derive を別ファイル形態で起動)。 機械 SSoT が唯一の真実源・人間プレゼンは派生 view であり、 同期は更新日時 + fidelity gate で追跡する (co-author = enforcement から生成 = 検証への移行)。
  • ハイブリッド生成 (ADR-0042 §2.1) — 決定的 assembler が構造化された入力 contract (要件レコード = 一意 id / 型 (FR/NFR/CON/ASM) / EARS clause / トレース端点 / 根拠出所、 加えて NFR メトリクス・用語・上位ニーズ) を読み、 文書の構造 (要件マトリクス・NFR 表・RTM グリッド・優先度/検証バッジ・被覆) を data-component 付きで組立てる。 RTM / トレースの各セルはトレースデータから決定的に導出するため、 元に無い行・列・リンクの捏造は構成上不可能になる (fabrication-free-by-construction)。 これが機械/LLM 検証境界の一次根拠である: 構造捏造が構成上排除済ゆえ機械 floor は捏造を census せず、 意味的忠実性 (捏造・矛盾) と可読性は独立 LLM reviewer の ceiling が裁き、 決定的 census・静的 hidden-render ban は構成上排除済の脅威を再検査する warn 級 backstop に留める (別建ての決定的安全網を後付けしない)。 gate 割当・blocking arm と warn 級 backstop の区分・REQ-VER 形式化の SSoT は srs-verification (本 §12 は境界の WHAT を定め gate を個別列挙しない・P-7)。 高能力モデルは assembler が空で残した prose スロットのみ充填する (章リード / 「なぜ要る」根拠 / 専門語のやさしい併記 / 1 文サマリ)。 構造は SSoT から毎回決定的に再組立し、 構造に差分編集を介在させない (更新は prose 層でのみ差分再生成する)。
  • 成果物の自己完結性 — 生成プレゼンは自己完結の static HTML + CSS + inline SVG + vendored mermaid とし、 外部 URL / CDN / ES module に依存しない (no-build・AI 直読・file:// 動作、 §8 JS governance / P-13 と整合)。
  • 2-gate 検証 + floor 刷新 — done-condition は二層で判定する: GREEN ⟺ (floor 全通過) AND (ceiling 合格)。 floor 単独で GREEN を宣言しない (存在だけ測って中身を測らない Goodhart 再発の構造防止 = ADR-0040 の「長さだけ測って読めない」死角の是正)。 floor 刷新 (ADR-0041 §2.5): 人間層 floor を「人間可視 prose の長さ (字数)」から「visual-first (地の文偏重の禁止) / 用語被覆 (未説明の専門語ゼロ) / renders-unbroken (render-gate)」+ 構造の存在・完全性へ刷新する (長さ time-box は本 floor が置換)。 floor = 決定的 (機械判定・blocking)、 ceiling = LLM (persona walk = 非エンジニアが頑張れば読めるか〔専門エンジニア水準では不合格〕 / fidelity check = 機械 SSoT との突合で情報落ち・歪み・捏造を検出 / completeness critic = 機械 SSoT の求める意味内容の被覆 — lens 詳細・gate 割当は srs-verification)。 二層は ADR-0028 の enforcement 二層と同型。 gate の形式化 SSoT は srs-verification.html (REQ-VER-024〜REQ-VER-029: folio verify-srs が floor 通過時に CEILING=PENDING を返す機械担保を含む)。 本章は WHAT 規律を定め、 gate を個別列挙しない (P-7、 gate 詳細は verification に集約)。

SRS doc-type パック規律 (29148 接地・SRS 固有):

design system は再利用可能な部品庫で、 dual-audience の境界が部品単位へ降りる (各部品が機械精密スロットと設計された人間の顔を持つ)。 SRS 核 (γ scope) は ISO/IEC/IEEE 29148 で完全性を錨留めし、 部品 taxonomy の設計 SSoT は srs-component-taxonomy.html (37 部品の register 分類)、 部品庫の HOW 実装は design-system catalog が持つ (folio 自身の ADR / research / 原則は拡張パックで後追い)。

密系部品の非エンジニア可読化は assembler が 3 戦略に振り分けて構造的に保証する (ADR-0042 §2.2)。 高密度は fidelity の背骨として全 DOM 保持・展開可のまま残し、 主役の配置のみを変える:

  • allowlist の SSoT は catalog / taxonomy — 全 dense 部品の A / 据置 完全カタログ (部品 id allowlist) の SSoT は design-system catalog / taxonomy とし、 rules は振り分けの WHAT 規律のみ定め部品 id 列を複製しない (P-7)。 SHOULD 部品のスロットは MUST-when-present (出力に含まれる時のみ非空を hard-require)。
  • 用語被覆 — 専門語の本文中 plain 併記 (plain-language-term-inline) は用語定義表 (glossary-term-table) の派生ビューであり、 両者の定義一致を fidelity が検証する (double-SSoT 回避、 §9.5 glossary 機構と整合・用語定義の edit-SSoT 帰属は §9.5 carve-out に従う・ADR-0052)。
