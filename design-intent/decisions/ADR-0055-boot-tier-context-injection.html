ADR-0055 — SessionStart 注入の boot 予算適合 (Tier 0 pointer digest)

Status: accepted · Date: 2026-08-02 · folio v1.2.0 · SessionStart hook が boot 時に注入する内容を Tier 1 inventory digest から Tier 0 pointer digest (総数・rollup・tier pointer・照会 graph digest のみ) へ変更する。 folio prime (既定) の Tier 1 emit は不変で on-demand 開示の実行経路として存続し、 ADR-0007 §2.2 の「注入内容 = Tier 1」は本 ADR が supersede する。 動機は corpus 成長後の Tier 1 出力が boot 注入予算 (10,000 UTF-16 code unit 超で file 退避) を超え boot context に全文が届かなくなったこと (2026-08-02 実測 29,970 UTF-16 code unit、 詳細 §1)。 Three-Tier Progressive Disclosure Model 自体は不変で、 Tier 0 は boot 予算適合のための Tier 1 への pointer 形。 conformance は prime-boot golden と REQ-VER-012 整合が持つ。

§1. Context

ADR-0007 (2026-05-25) は SessionStart hook → folio prime stdout の context 注入を設計し、 §2.2 で注入内容を Tier 1 inventory digest (compact text、 当時想定 ~1-2k tokens) と定めた。 本 ADR で boot = SessionStart hook が発火する fresh session の起動時点を指す。 数量の単位は byte ではなく UTF-16 code unit である (以下 unit と略す)。

その後 corpus は 62 spec へ成長し、 folio prime 出力は実測 29,970 unit (2026-08-02 admin 実測。 scriptorium 横断監査 orch-gg24 の実測 23,902〜29,970 と整合) に達した。 超過の内訳は per-spec 一覧が約 2/3、 ADR-0034 で追加された object-graph index (126 canonical objects) が約 1/4 で、 後者は spec 数でなく canonical object 数で増える。 relations.html §4.2 の Tier 1 目安 (30-50 tokens per spec) は per-spec 実測でも総量でも超過した。

Claude Code harness (2026-08-02 時点の挙動) は SessionStart 注入が 10,000 unit を超えると本文を file へ退避し preview (約 2,000 unit 相当) のみを context に注入する — 以下この境界を boot 注入予算 と呼ぶ。 本決定前の boot は「Tier 1 の注入 cost を払いながら、 実際には冒頭 preview しか届かない」状態だった = ADR-0007 が意図した「fresh session が inventory を即座に持つ」効果は失われていた。

Tier 0 形のプロトタイプ実測 (2026-08-02) は 848 unit — boot 注入予算 10,000 に対し 1 桁小さく、 §2.1 の構造規定 (行数一定) の実証点である。

§2. Decision

§2.1 boot 注入 = Tier 0 pointer digest

SessionStart hook (inject-inventory.sh) は folio prime --boot の stdout = Tier 0 pointer digest を注入する。 構成要素 (WHAT の normative は REQ-VER-012 が持ち、 本節は決定の記録):

  • header 行 — spec 総数・folio version・dir 内訳 (spec / decisions / research)。 先頭行は canonical 名「Tier 0 pointer digest」を名乗る (逐語の SSoT は prime-boot golden)
  • rollup — doc-type 内訳 1 行 + status 内訳 1 行
  • tier pointer — Tier 1 (per-spec 一覧 + object-graph index) は folio prime を on-demand 実行、 Tier 2 (各 spec の <head> + 冒頭段落)・Tier 3 (spec 本文全体) は該当 spec を on-demand Read、 関係の詳細 (objectGraph の全 node/edge) は inventory.json を Read、 の誘導 2 行
  • 照会 graph digest — nodes/edges 数 + 被参照数 top 10。 top 10 の導出 query と行形式は Tier 1 digest 末尾と同一 (header 行のみ 1 行へ圧縮)。 ADR-0043 §2.3 tier1 (照会 graph digest の常時 baked) の要件を Tier 0 でも満たすための保持であり、 将来 Tier 0 を削る編集はこの要件を破らないこと

Tier 0 の出力量は構成上 spec 数に依存しない — rollup と top 10 は corpus が成長しても行数一定 (実質 O(1)) で、 boot 注入予算を下回り続ける (実測は §1)。

§2.2 folio prime (既定) は Tier 1 のまま不変

folio prime (引数なし既定) は従来どおり Tier 1 inventory digest を emit する。 REQ-VER-012 の SHALL (CLI SHALL emit a Tier 1 inventory digest) は維持され、 prime-digest.yaml の scenario・比較方式も不変 (corpus 追加に伴う golden 再生成は従来どおり各 land に同梱する)。 Tier 0 の pointer が指す on-demand 開示の実行経路そのものであり、 boot 注入予算の制約は hook 経路にのみ存在する (手動実行の stdout は予算対象外)。

§2.3 ADR-0007 との関係 (partial supersede)

ADR-0007 §2.2 「注入内容 = Tier 1 inventory digest」 は本 ADR §2.1 が supersede する。 ADR-0007 の他の決定は不変: §2.1 mechanism (SessionStart hook → prime stdout、 matcher 省略 = 全 source 発火)、 §2.3 (CLI は手動 entry point でもある)、 §2.4 (staleness auto-regen — --boot も同一の regen 判定・再生成経路を共有する)。 変わるのは hook が prime へ渡す mode 引数 (--boot) のみで、 CLI の既定動作は §2.2 のとおり Tier 1 のまま mode が加わる。 部分 supersede は ADR-0026 先例に従い dc:replaces でなく dc:references + 本節/§5 の trace で記す (frozen ADR-0007 本文は P-6 のもと不触・逆リンクのみ)。

§2.4 Three-Tier Progressive Disclosure Model は不変

relations.html §4.2 の Three-Tier Progressive Disclosure Model は不変。 Tier 0 は spec 内容の新しい開示粒度ではなく、 boot 注入予算に適合するための「Tier 1 (index) への pointer 形」 であり、 spec 内容の開示は従来どおり Tier 1 → 2 → 3 で行う。

§2.5 Conformance

本決定の整合面は次のとおり (いずれも決定後の世界の不変条件として述べる):

  • Tier 0 出力は tests/scenarios/prime-boot.yaml (kind: cli-golden、 capture: stdout、 compare: text) の golden と byte-exact 一致する — header 逐語の SSoT はこの golden。
  • REQ-VER-012 は statement (--boot の SHALL 条項) と人間層 (essence・平易行) の両層で本決定に整合する (contract 経由で保持。 harness 固有の予算定数は spec 側に literal で置かず本 ADR §1 を照会する)。
  • relations.html §0 の data-pipeline 図は本決定に整合する (contract 経由。 Tier 0 注入を主線、 Tier 1 を on-demand 分岐として描く)。
  • e2e S-F (tests/e2e/runbook.md と tests/e2e/README.html の S-F 行) の期待観察は Tier 0 pointer digest の header を先頭に受領すること。 observations-sessionstart.json は 2026-05-25 時点の観察記録として据置き、 Tier 0 の実注入 record は次回 S-F walk で追加する。
  • folio-self-spec.html §3.1 の注入記述は本決定に整合する。
  • glossary の prime 定義 (contract 経由・ADR-0052) の整合改訂は follow-up として trace する (§5)。

§3. Consequences

  • (+) boot 注入は常に boot 注入予算内 — file 退避されず、 preview 断片でなく digest 全文が context に届く。
  • (+) prime stdout の生成量は Tier 1 全量比で 1 桁以上小さい (2026-08-02 実測 848 / 29,970 unit)。
  • (+) corpus が成長しても Tier 0 は行数一定 (rollup + top 10) で、 本問題は再発しない。
  • (−) fresh session は per-spec 一覧を自動では持たない — Tier 0 の pointer が folio prime の on-demand 実行 (1 コマンド) を明示誘導する。
  • (−) bin/folio と inject-inventory.sh は plugin 部品のため、 land 後に plugin cache sync が必要。

§4. Alternatives Considered

  • (a) 現状維持 — boot 注入予算の超過で preview しか届かず、 注入 cost だけを払い続ける。 却下。
  • (b) hook 側 truncation — 予算内に頭から切り詰める。 どの spec が届くかが列挙順依存で非原理的。 却下。
  • (c) Tier 1 の項目削減 — per-spec の title/summary を落とす。 REQ-VER-012 の項目列挙を破壊し、 かつ object-graph index を含む残量だけで概算 15k UTF-16 code unit となり予算超過が続く。 却下。
  • (d) 分割注入 — 複数 hook へ分けて届く量を増やす。 総 token は増える方向で予算問題の解にならない (orch-gg24 の指摘どおり第一選択でない)。 却下。
